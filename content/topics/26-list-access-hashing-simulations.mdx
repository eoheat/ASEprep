## Intuition

Three loose ends that tie the course together. First, *why* is list indexing
`Theta(1)` — what does the machine actually do? Second, *why* is dictionary lookup
`Theta(1)` on average — the magic word is **hashing**. Third, **simulations**: when
a problem is too messy to solve with math, you can approximate the answer by running
a randomized experiment many times and averaging. All three are about turning
abstract complexity claims from earlier units into concrete mechanisms.

## The mechanics

**Constant-time list access.** A list of `n` items reserves a consecutive block of
memory, a fixed number of bytes per slot. The list variable points to the first
slot. To reach element `i`, Python computes `start + (slot_size * i)` and jumps
straight there — one arithmetic step, no scanning. That's why `L[i]` is `Theta(1)`
regardless of `n`. For a heterogeneous list, each slot stores a *pointer* to the
real object rather than the object itself, but the indexing arithmetic is identical,
so it's still constant.

**Hashing.** A dictionary is a **hash table**. A *hash function* converts a key into
an integer, and that integer (mod the table size) is the index into an underlying
list:

```python
hash(123)               # 123
hash("6.100L is awesome")   # some large int, deterministic within a run
hash((1, 2, 3))         # works: tuples are hashable
hash([1, 2, 3])         # TypeError: unhashable type: 'list'
```

Convert key → integer (constant), index into the list (constant), read the value
(constant). So dictionary lookup is `Theta(1)` — *on average*.

A tiny hash function, to build intuition: sum a name's letters, take mod 16 to fit a
16-slot table.

```python
# 'Ana' -> 1 + 14 + 1 = 16, 16 % 16 = 0     -> slot 0
# 'Eric' -> 5 + 18 + 9 + 3 = 35, 35 % 16 = 3 -> slot 3
# 'Eve' -> 5 + 22 + 5 = 32, 32 % 16 = 0      -> slot 0  (collision with Ana!)
```

When two keys land in the same slot, that's a **collision** — the slot holds a small
list of everything that mapped there, searched linearly. Rare collisions keep lookup
constant; if *everything* collides, lookup degrades to `Theta(n)` (the very rare
worst case).

<Callout type="note">
A good hash function: maps into `0..table_size`, is fully determined by the value
(nothing random), uses the whole input (fewer collisions), and spreads values
uniformly. Keys must be **hashable = immutable** — that's why dict keys can be
strings, ints, and tuples, but not lists.
</Callout>

**Simulations.** When the math is hard, model the event with randomness, repeat many
times, and report the fraction of interest.

```python
import random

def prob_dice(side):
    dice = ['.', ':', ':.', '::', '::.', ':::']
    Nsims = 10000
    count = 0
    for i in range(Nsims):              # repeat the experiment
        roll = random.choice(dice)      # design the experiment
        if roll == side:                # track the outcome
            count += 1
    return count / Nsims                # report the value of interest
```

The recipe is always: observe an event, design an experiment, repeat it `K` times in
a loop, count outcomes, divide by `K`.

## Worked example

A question that's genuinely annoying to solve with math but trivial to simulate:
water fills a pool at a random rate between 1 and 3 gallons/min. How long to fill a
600-gallon pool on average? Intuition says 300 min (600/2) or 400 min — both wrong.

```python
import random

def fill_pool(size):
    fill_times = []
    Npoints = 10000
    for i in range(Npoints):
        rate = 1 + 2 * random.random()   # random rate in [1, 3)
        fill_times.append(size / rate)   # time = size / rate
    return sum(fill_times) / len(fill_times)

print(fill_pool(600))     # approx. 331 minutes
```

The average rate is ~2 gal/min (as expected), but the average *fill time* is ~331
min, not 300. The reason: fill time is `size / rate`, an **inverse** relationship, so
slow rates (which take disproportionately long) pull the average up. Solving this
exactly needs an integral; the simulation needs five lines.

## Traps

<Callout type="trap">
**`Theta(1)` for dict lookup is *average* case, not guaranteed.** With a good hash
function and enough slots, collisions are rare and lookup is constant. But if all
keys hash to the same slot, it degrades to a linear scan, `Theta(n)`. The exam
distinguishes "average case `Theta(1)`" from "worst case `Theta(n)`."
</Callout>

**Dict keys must be immutable/hashable.** `hash([1,2,3])` raises `TypeError` —
lists can't be keys because their contents (and thus their hash) could change. Use a
tuple instead. This is the practical face of "keys must be hashable."

**The average of `f(random)` is not `f(average)`.** In the pool problem, average
rate ~2 does *not* give average time = 600/2 = 300. Because time = size/rate is
nonlinear, you must average the *outcomes*, not plug the average input into the
formula. This is the whole point of simulating.

**More simulation runs → more accuracy, but never exact.** `Nsims = 10000` gives an
estimate that jitters run to run. Increasing it tightens the estimate; it never
gives the precise analytic answer. That's the trade-off simulations make.

## Memorize vs understand

| Just know it cold | Be able to derive |
|---|---|
| `L[i]` is `Theta(1)`: `start + slot_size * i`, direct jump | Why list indexing is constant even for a huge or heterogeneous list |
| Dict = hash table; lookup `Theta(1)` average, `Theta(n)` worst | Why worst-case dict lookup degrades (all keys collide) |
| Dict keys must be hashable = immutable (str, int, tuple; not list) | What makes a hash function "good" (uniform, full-input, deterministic) |
| Simulation recipe: experiment → loop K times → count → divide | Why `avg(size/rate) != size/avg(rate)` for the pool problem |
| `random.choice(seq)`, `random.random()` in `[0, 1)` | How collisions are handled (a list per slot, linear search within) |

Unit 4 operations-cost table:

| Operation | Cost |
|---|---|
| list index `L[i]` | O(1) |
| list append `L.append(x)` | O(1) amortized |
| list `in` / `insert` / `delete` / `copy` | O(n) |
| dict / set lookup, insert, `in` | O(1) average |
| sort (`sorted`, `.sort`) | O(n log n) |
| linear search | O(n) |
| bisection (binary) search | O(log n) |
| bubble sort | O(n^2) |
| merge sort | O(n log n) |

This lecture explains *why* the list and dict rows hold: consecutive memory + index
arithmetic gives O(1) list access; hashing gives O(1) average dict access, which is
exactly why `x in some_set` beats `x in some_list` when you search repeatedly.

## ASE check

<ASECheck q="Why is L[i] constant time no matter how large the list is?">

A list occupies a consecutive block of memory with a fixed number of bytes per slot,
and the list variable points to the start. To reach element `i`, Python computes
`start + slot_size * i` and jumps there directly — one arithmetic step, no scanning.
So access is `Theta(1)` independent of `len(L)`.

</ASECheck>

```python
hash([1, 2, 3])
```

<ASECheck q="What happens here, and why?">

It raises `TypeError: unhashable type: 'list'`. Dictionary keys and hashable objects
must be immutable, because a hash must be stable — a list's contents can change, which
would change its hash and break lookups. Use a tuple `(1, 2, 3)`, which is hashable.

</ASECheck>

<ASECheck q="Dictionary access is often quoted as Theta(1). When is it not, and why?">

It's `Theta(1)` only on *average*. In the rare worst case — when the hash function is
poor or the table is too small and all keys collide into one slot — lookup becomes a
linear scan of that slot, `Theta(n)`. Good hashing (uniform, using the whole key,
large-enough table) keeps collisions rare so the average stays constant.

</ASECheck>

<ASECheck q="A pool fills at a random rate between 1 and 3 gal/min. The average rate is 2, so is the average fill time for a 600-gallon pool simply 600/2 = 300 minutes?">

No — it's about 331 minutes. Fill time is `size / rate`, a nonlinear (inverse)
relationship, so you cannot plug the average rate into the formula. Slow rates take
disproportionately long and pull the average time above 300. You have to simulate:
average the *fill times*, not compute the time from the average rate.

</ASECheck>
